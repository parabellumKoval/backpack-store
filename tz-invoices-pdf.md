# ТЗ: Подсистема генерации PDF‑счетов (Laravel 12, пакет `backpack/store`)

**Проект**: Laravel Backpack Store  
**Версия Laravel**: 12.x  
**Пакет**: `parabellumkoval/backpack-store`  
**Назначение**: Генерация PDF‑счетов «1:1 как в примере PDF», автогенерация QR на оплату, предпросмотр/скачивание из фронта и админки, отдельная выдача QR для заказа.

> 📎 Макет (визуал и тексты) берём буквально из присланного PDF. В ТЗ не дублируем HTML – использовать _точный_ шаблон по PDF, который будет приложен к задаче как файл.  
> 📎 Пример файла: `vivadzen-2025-10-0033.pdf` (будет приложен к ТЗ).

---

## 1. Цели и задачи

- Сформировать **подсистему счетов** в пакете `store`, которая:
  1) создаёт **PDF‑счета** по данным заказа;
  2) **автоматически** генерирует **QR** для оплаты (до вставки в PDF);
  3) позволяет **просматривать** и **скачивать** PDF по существующим заказам (API и админка);
  4) предоставляет **отдельную выдачу QR** по заказу (API и админка);
  5) поддерживает **разные шаблоны** (минимум 1 – «как в примере PDF»).

---

## 2. Область работ и ограничения

- Работы в рамках пакета `backpack/store` с учётом структуры проекта (см. структуру в инструкции).
- **Не фиксировать конкретные библиотеки** PDF/QR в коде ТЗ – описываем функциональность. Реализация может использовать любую совместимую библиотеку, работающую на PHP 8.2+ и Laravel 12.
- Вёрстка PDF должна **полностью соответствовать** приложенному примеру (шрифты/отступы/сетки/подписи/язык). Источник истины — **PDF‑макет**.
- Логотип, «мокрая печать», подпись и т.п. — **слоты**, значения приходят из настроек/конфига/БД (URL или путь), и **не жестко зашиваются** в шаблон.
- QR с параметрами оплаты — **обязательно** генерируется **перед** рендером PDF (подробнее ниже).

## 3. Бизнес‑логика

### 3.1. Откуда берём данные для счёта
- Источник: существующая модель **Order** (внутри пакета/проекта).  
- Минимальные поля/сущности, которые требуются подсистеме (получаем из Order либо связанных моделей):
  - **Реквизиты продавца**: название, IČO/DIČ (если есть), адрес (улица/город/индекс/страна), платёжные реквизиты (номер счёта, IBAN, BIC/SWIFT, банк).
  - **Реквизиты покупателя**: наименование ФЛ/ЮЛ, адрес. (ИНН/НДС‑номер — опционально, если есть).
  - **Заказ**: номер заказа (для вариабельного символа), номер счёта, даты: `issued_at` (выписки), `due_at` (срок оплаты), `taxed_at` (дата налогового события), валюта, позиции (наименование, кол-во, единица, цена за ед., ставка НДС/DPH, сумма без НДС), итоги (сумма без НДС, НДС, всего к оплате).
  - **Страна/регион** заказа (для выбора платёжных реквизитов/локали/форматов).
- Если каких‑то данных в `Order` нет — подсистема получает их из **настроек Store** (см. §7).

### 3.2. Шаблоны PDF
- Система поддерживает **множественные шаблоны**. В ТЗ требуется **1 шаблон**, **идентичный приложенному PDF** («чешский макет»).
- Выбор шаблона:
  - По умолчанию — «чешский макет».
  - В будущем — по стране заказа/настройкам.
- **Структура полей и визуал** в PDF — как в приложенном файле: шапка с типом документа и номером, блоки «Dodavatel/Odběratel/Platební údaje», три даты, таблица позиций с колонками, итоговая сводка по ставкам DPH и общей сумме, итоговая «Částka k úhradě», зона для QR/печати/подписи, сопроводительные пометки (например, «Daňový doklad», «Číslo objednávky …», «Děkujeme» и т.д.).  
- **Язык подписей** — чешский (точно как в PDF).

### 3.3. Локализация и форматирование
- Для «чешского макета»:  
  - формат даты: `d. m. Y` (например, `23. 10. 2025`),  
  - валютные форматы: `CZK`, разделители и пробелы — как в примере PDF,  
  - десятичная точность: 2 знака по деньгам, количество — по бизнес‑правилу (обычно 0/2).  
- В будущем должна быть возможность добавить ES/DE макеты с собственными локалями/форматами.

### 3.4. Генерация QR (обязательная, до PDF)
- QR генерируется **автоматически** при создании/просмотре счёта **до рендера PDF**.
- Требуемый формат полезной нагрузки (payload) **строго по заданию**:  
  `SPD*1.0*ACC:<IBAN>*AM:<amount.2f>*CC:<currency>*X-VS:<variableSymbol>*MSG:<message>`  
  Пример:  
  `SPD*1.0*ACC:CZ3355000000001177755577*AM:1650.00*CC:CZK*X-VS:20447*MSG:TEST`
- Поля:
  - **ACC** — IBAN получателя (берётся из реквизитов продавца для страны/региона заказа).
  - **AM** — сумма итога к оплате (2 знака).
  - **CC** — буквенный код валюты (ISO 4217), например `CZK`.
  - **X‑VS** — вариабельный символ (как правило, `order_number`).
  - **MSG** — короткое произвольное сообщение (например, `Faktura <invoice_number>` или `TEST` — см. настройки).
- Выход QR — **растровый PNG** или **векторный SVG** (предпочтительно SVG для качества в PDF).  
- QR хранить **каширoвано** (по ключу `order_id` + хэш полезной нагрузки). При повторном запросе — отдать из кэша/диска.

> Примечание: Заказчик осознанно требует строку формата **SPD** даже для европейских стран (CZ/ES/DE). Если для ES/DE понадобится формат EPC/SEPA (BCD) — будет отдельная задача. В рамках текущего ТЗ генерируем **ровно SPD** по заданной спецификации.

### 3.5. Сценарии использования
1) **Предпросмотр PDF** по существующему `order_id` (без сохранения файла):  
   - API: возвращает `Content-Type: application/pdf`, `inline` отображение.
2) **Скачать PDF** (с сохранением на диск и/или ссылкой):  
   - API: `Content-Disposition: attachment` или ссылка на ранее сохранённый файл.
3) **Получить QR** по `order_id`:  
   - API: возвращает изображение QR (`image/svg+xml` или `image/png`).
4) **Админка Backpack**:
   - В карточке заказа: кнопки «Предпросмотр PDF», «Скачать PDF», «Показать QR».
   - В списке заказов — массовое действие «Сгенерировать PDF» (опционально).

## 4. API и маршруты (черновой контракт)

Все маршруты под `/api/store/invoices` (можно уточнить префикс в пакете).  
Авторизация/права — см. §6.

- `GET  /api/store/invoices/{order}` — **предпросмотр PDF** (inline).
  - Параметры: `template` (опц.), `locale` (опц.).
  - Ответ: `200 PDF` (inline).
- `GET  /api/store/invoices/{order}/download` — **скачать PDF**.
  - Параметры: `template` (опц.).
  - Ответ: `200 PDF` (attachment) ИЛИ `302 Location: <public-url>` если файл заранее сохранён.
- `GET  /api/store/invoices/{order}/qr` — **получить QR**.
  - Параметры: `format=svg|png` (по умолчанию `svg`).
  - Ответ: `200 image/svg+xml` или `image/png`.

> Имена/префиксы можно скорректировать под общие правила API проекта.

## 5. Админка (Backpack)

- **Кнопки‑действия** в Order CRUD:
  - «Предпросмотр PDF» — открывает в новом окне inline PDF.
  - «Скачать PDF» — триггерит скачивание.
  - «Показать QR» — модал/панель с QR.
- **Права/политики**: действия доступны ролям с правами `order.view` / `order.download_invoice` / `order.view_qr` (настройка мидлваров).
- **Логи**: действие фиксировать в журнале (кто/когда сформировал/скачал).

## 6. Доступ и безопасность

- API защищено: требуется авторизация (токен/сессия) и проверка прав:
  - Предпросмотр PDF: доступ владельцу заказа и админам.
  - Скачивание PDF: доступ владельцу заказа (для вложения в e‑mail — будет публичная ссылка с **подписанным URL** и TTL) и админам.
  - Просмотр QR: владелец заказа и админы.
- Публичные ссылки на PDF (для e‑mail) — **подписанные маршруты** с ограничением по времени (TTL настраиваемый).

## 7. Настройки/конфиг

- Группа настроек пакета `store.invoices.*`:
  - `store.invoices.default_template` — ключ шаблона (по умолчанию «cz/fakturoid-like»).
  - `store.invoices.locale` — локаль форматирования (по умолчанию `cs_CZ`).
  - `store.invoices.currency` — валюта по умолчанию (`CZK`).
  - `store.invoices.assets.logo_url` — URL лого (опц.).
  - `store.invoices.assets.stamp_url` — URL «мокрой печати» (опц.).
  - `store.invoices.qr.message_pattern` — шаблон сообщения в QR (например, `Faktura {invoice_number}`).
  - `store.invoices.qr.cache_disk` и `cache_ttl` — куда и на сколько кэшировать QR.
  - `store.invoices.storage.disk` — диск для хранения PDF.
  - `store.invoices.storage.path_mask` — маска пути, например: `invoices/{Y}/{m}/{invoice_number}.pdf`.
  - `store.invoices.bank_accounts` — карта реквизитов по стране/региону:
    ```jsonc
    {
      "CZ": {
        "iban": "CZ3355000000001177755577",
        "bic":  "RZBCCZPPXXX",
        "account_display": "1177755577/5500",
        "bank_name": "Raiffeisenbank"
      },
      "DE": { "iban": "...", "bic": "...", "bank_name": "..." },
      "ES": { "iban": "...", "bic": "...", "bank_name": "..." }
    }
    ```
- В админке Backpack — страница настроек для заполнения этих параметров.

## 8. Хранение и жизненный цикл файлов

- **QR**: кэшируется на диске/в БД по ключу нагрузки; при изменении суммы/валюты/VS — пересчитывается.
- **PDF**: может генерироваться на лету (предпросмотр) и/или сохраняться на диск:
  - При первом «скачать» — сохранять файл и отдавать ссылку.
  - Возможность **регенирации** по требованию (флаг «пересоздать», если данные заказа изменились).

## 9. Точки интеграции

- **E‑mail клиента**: в письмо по заказу добавляется ссылка на **подписанный URL скачивания PDF**.
- **Webhook/События** (опц.): `InvoiceGenerated`, `InvoiceDownloaded`, `InvoiceQrGenerated` — для аудита/интеграций.

## 10. Нефункциональные требования

- Производительность: генерация PDF и QR не должна блокировать UI админки; при массовой генерации — через очередь (опц.).
- Совместимость: PHP 8.2+, Laravel 12, Backpack 5.x/совместимая.
- Логи/метрики: ошибки генерации логируются с привязкой к `order_id`.
- Тесты: минимум **Feature‑тесты** для 3 маршрутов (предпросмотр, download, qr).

---

## 11. Тест‑кейсы (acceptance)

1) **Предпросмотр PDF** существующего заказа:
   - Вызов `GET /api/store/invoices/{order}`.
   - Ожидается `200` и `application/pdf` (inline).
   - Визуально PDF **совпадает** с приложенным образцом (с учётом динамических данных).
2) **Скачать PDF**:
   - `GET /api/store/invoices/{order}/download` -> скачивание файла.
   - Повторный вызов может отдавать ранее сохранённый файл.
3) **Получить QR**:
   - `GET /api/store/invoices/{order}/qr?format=svg` -> `200 image/svg+xml`.
   - Поменяли сумму/валюту/VS — QR меняется.
4) **Админка**:
   - В заказе есть кнопки «Предпросмотр PDF», «Скачать PDF», «Показать QR».
   - Доступ по ролям.
5) **E‑mail**:
   - Сформирован корректный подписанный URL на скачивание, работает в течение TTL.

## 12. Сопоставление полей (минимум)

| Бизнес‑поле в PDF                         | Источник                                                                 |
|------------------------------------------|--------------------------------------------------------------------------|
| Номер счёта (invoice number)             | `Order.invoice_number` или вычисляется сервисом                         |
| Номер заказа / Variabilní symbol         | `Order.number` (или `Order.id`)                                         |
| Даты: vystavení, splatnosti, zdan. plnění| `Order.issued_at`, `Order.due_at`, `Order.taxed_at`                     |
| Продавец (адрес/ICO/DIC/банк)            | Настройки по стране заказа `store.invoices.bank_accounts[order.country]` + настройки продавца |
| Покупатель                               | `Order.customer` (ФИО/название, адрес)                                   |
| Позиции                                  | `Order.items` (name, qty, unit, price, vat_rate, total_ex_vat)          |
| Итого без НДС / НДС / Всего              | Расчёт по позициям или `Order.totals`                                    |
| Валюта                                   | `Order.currency`                                                         |
| QR payload                               | Собирается сервисом из итогов и реквизитов                               |

## 14. Оценочные риски и уточнения

- Если в ES/DE потребуется иной формат QR (EPC/SEPA), будет отдельная подзадача.
- Линки на логотип/печать могут быть как абсолютные URL, так и `storage`‑пути — необходимо предусмотреть `isRemoteEnabled`/чтение с диска.

---

## 15. Критерии приёмки

- PDF визуально **совпадает** с эталонным файлом при одинаковых данных.
- QR генерируется **до** вставки в PDF, payload соответствует спецификации `SPD*1.0*...`.
- Предпросмотр/скачивание/QR работают по API и из админки, с корректными правами.
- Ссылка для e‑mail на скачивание PDF — подписанный URL с TTL.
- Набор тестов проходит (минимум 3 функциональных).
